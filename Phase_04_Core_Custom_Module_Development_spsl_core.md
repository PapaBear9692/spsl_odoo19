## 1. PHASE OVERVIEW

### 1.1 Purpose

Phase 4 develops **spsl_core**, the foundational custom Odoo 19 CE module upon which ALL other SPSL custom modules (spsl_mps, spsl_field_engineer, spsl_foreign_purchase, spsl_bangladesh_compliance, spsl_payroll_bd, spsl_portals) depend. This module provides shared, cross-cutting services that are consumed by every downstream module: a configurable approval engine with maker-checker enforcement, an immutable cryptographic audit trail, a multi-channel notification framework, multi-branch data isolation record rules, and a commission calculation engine.

No business-domain module (MPS billing, field engineer job cards, payroll processing) is developed in this phase. Phase 4 is exclusively concerned with the shared infrastructure layer — the "platform within the platform" — that enables all subsequent domain modules to inherit approval workflows, audit logging, notification dispatch, branch isolation, and commission computation without reimplementing these capabilities.

### 1.2 Scope

| In Scope | Out of Scope |
|---|---|
| spsl_core module scaffold (__manifest__.py, directory structure, base mixins) | Domain-specific modules (spsl_mps, spsl_field_engineer, etc.) |
| Approval engine: data models, workflow state machine, escalation, maker-checker | Approval rule configuration for specific business documents (done in later phases) |
| Immutable audit trail with SHA-256 hash chain and 7-year retention | Audit reporting dashboards (done in Phase 12 — BI & Reporting) |
| Notification framework: dispatcher, templates, 56 event catalogue | SMS gateway live integration (Mutho API — done in Phase 13) |
| Multi-branch data isolation record rules via operating_unit | Branch-specific business logic |
| Commission calculation engine (rules, entries, aggregation) | Payroll integration for commission payout (done in Phase 9 — HR/Payroll) |
| Unit tests (80%+ coverage) and integration tests for all spsl_core components | End-to-end UAT with SPSL users (done in Phase 14 — SIT/UAT) |

### 1.3 Timeline Context

This phase maps to Sprint 3 (partial) and Sprint 4 in the Project ELEVATE Sprint Plan. spsl_core must be fully operational before any downstream module development begins in Phase 5 (Finance & Accounting).

| Sprint Alignment | Sprint Dates | Phase 4 Work |
|---|---|---|
| Sprint 3 (S3) | May 5–18, 2026 | Milestones 4.1, 4.2, 4.3 (module scaffold, approval engine) |
| Sprint 4 (S4) | May 19 – Jun 1, 2026 | Milestones 4.4, 4.5, 4.6, 4.7 (audit trail, notifications, data isolation) |
| Sprint 5 (S5) | Jun 2–15, 2026 | Milestones 4.8, 4.9, 4.10 (commission engine, testing, sign-off) |

### 1.4 Critical Path Significance

spsl_core sits on the **critical path** of the entire SPSL ERP implementation. Every custom module developed in Phases 5 through 11 declares `spsl_core` as a dependency in its `__manifest__.py`. A delay in Phase 4 cascades directly to all downstream phases:

- Phase 5 (Finance) needs ApprovalMixin for journal entry and payment approvals
- Phase 6 (Sales/CRM) needs commission engine and approval workflows
- Phase 7 (Purchase) needs maker-checker and audit trail
- Phase 8 (MPS) needs notification framework for contract alerts
- Phase 9 (HR/Payroll) needs commission entries for payroll integration
- Phase 10 (Field Engineer) needs notification dispatch for SLA alerts
- Phase 11 (Portals) needs notification preferences and data isolation

## 5. RISK REGISTER

| Risk ID | Risk Description | Probability | Impact | Mitigation Strategy | Owner |
|---|---|---|---|---|---|
| R4.01 | **ApprovalMixin inheritance conflicts with existing Odoo model inheritance chains.** Some standard Odoo models already use complex inheritance hierarchies (e.g., account.move inherits mail.thread, mail.activity.mixin). Adding ApprovalMixin may create MRO (Method Resolution Order) conflicts or field name collisions. | Medium | High | TL designs ApprovalMixin with carefully namespaced field names (prefix `spsl_approval_`) to avoid collisions. Test mixin inheritance on the three target models (sale.order, purchase.order, account.move) during integration testing (Milestone 4.10). If MRO conflicts arise, refactor ApprovalMixin to use delegation inheritance (_inherits) instead of Python multiple inheritance. | TL |
| R4.02 | **SHA-256 hash chain computation degrades performance at scale.** Each audit log entry requires reading the previous entry's hash, which is a sequential dependency. Under high write concurrency, this creates a bottleneck as multiple transactions contend for the "latest hash" read. | Medium | Medium | Implement hash computation using database-level advisory locks to serialize hash chain writes without blocking other transactions. Use PostgreSQL `pg_advisory_xact_lock()` with a fixed lock ID for the audit log table. Profile during performance testing (Task 4.10.5). If performance target (<50ms) is not met, consider batching hash computation or using a separate hash chain per model_name partition. | TL |
| R4.03 | **Notification dispatcher introduces latency on business transactions.** Synchronous notification dispatch during `create()`/`write()` calls may slow down user-facing operations (e.g., confirming a sale order triggers multiple notifications). | Medium | Medium | Implement notification dispatch as an asynchronous operation using Odoo's `@api.autovacuum` or `queue_job` (OCA) for non-critical notifications. For critical/mandatory notifications, use Odoo's built-in `mail.mail` queue (already async). Measure dispatch latency during integration testing. If >200ms, move all dispatching to background queue processing. | DEV |
| R4.04 | **OCA operating_unit module API changes between Odoo 18 and 19.** If the OCA module was ported from Odoo 18 with API changes (field renames, method signature changes), the spsl_core ir.rule and BranchMixin code may break. | Low | High | DEV reviews the OCA operating_unit module source code for Odoo 19 during Milestone 4.7 before writing record rules. Pin the OCA module to a specific Git commit hash in the deployment configuration. If API changes are detected, adapt spsl_core code accordingly. Maintain a compatibility layer if needed. | DEV |
| R4.05 | **Commission calculation edge cases: multi-currency orders, partial deliveries, returns.** The initial commission engine handles standard BDT orders. Multi-currency orders (USD, EUR for foreign purchase), partial deliveries, and sales returns require additional logic not covered in Phase 4. | Medium | Low | Phase 4 commission engine handles the 90% case (standard BDT domestic orders). Document known limitations: multi-currency commission conversion deferred to Phase 7 (Purchase/Foreign LC), partial delivery commission adjustment deferred to Phase 6 (Sales), return/credit note commission reversal deferred to Phase 6. Track as technical debt in the Phase 4 Completion Report. | DEV |
| R4.06 | **56 notification templates exceed manageable volume for 2-person team.** Creating detailed HTML body templates for all 56 events in a single milestone may be unrealistic. Template quality may suffer if rushed. | Medium | Medium | Prioritize: create full rich HTML templates for 15 critical events (NE-001, NE-003/004, NE-010–NE-013, NE-033/035, NE-050–NE-056) in Phase 4. Create basic text-only templates for remaining 41 events with placeholder bodies. Rich templates for non-critical events can be enhanced in later phases when the triggering modules are developed and real data is available. | DEV |
| R4.07 | **Audit log storage grows rapidly.** Every create/write/unlink on audited models generates a log entry with JSON payloads. In production with ~100 active users, this could generate thousands of entries per day, consuming significant database storage. | Medium | Medium | Implement JSON payload compression using Python `zlib` for old_values/new_values fields >1KB. Configure PostgreSQL table partitioning by month for spsl.audit.log (via `CREATE TABLE ... PARTITION BY RANGE`). Monitor storage growth during integration testing. The 7-year retention archival (Task 4.4.5) moves cold data to compressed archive table. Set up database monitoring alerts for audit table size. | TL |
| R4.08 | **Test environment data conflicts with unit tests.** Unit tests running on a database with existing Phase 3 configuration data may produce unexpected results (e.g., existing ir.rules interfering with data isolation tests, existing users matching test patterns). | Low | Medium | Use Odoo's `TransactionCase` which rolls back after each test, ensuring test isolation. For integration tests requiring specific data setups, use `setUp()` methods to create all required test data within the test transaction. Avoid relying on demo data. If conflicts persist, create a dedicated test database with minimal configuration for the CI pipeline. | DEV |
