## Completed Tasks

### Task 1: Approval Rule & Rule Line Models

**Status:** COMPLETED
**Priority:** High
**Category:** Backend / Database

#### Description
The approval engine lacked a threshold-based rule system. Previously, approvals were tied only to static levels and transitions, with no way to define monetary or numeric ranges that determine which approver group handles a request. This made it impossible to implement real-world scenarios like "orders under $1,000 need a team lead, orders over $1,000 need a manager."

#### Files Modified
- `custom_addons/spsl_core/models/approval/approval_rule.py` (new)
- `custom_addons/spsl_core/models/approval/__init__.py`
- `custom_addons/spsl_core/security/ir.model.access.csv`

#### Implementation Details
Created two new Odoo models: `spsl.approval.rule` and `spsl.approval.rule.line`.

**ApprovalRule** binds to a target model (e.g., `sale.order`) and specifies which field acts as the trigger (e.g., `amount_total`). It includes a dynamic selection method that queries `ir.model` at runtime to populate available models:

```python
@api.model
def _selection_model_name(self):
    models = self.env['ir.model'].search([
        ('transient', '=', False),
    ], order='name')
    return [(m.model, m.name) for m in models]
```

A constraint validates that the `field_trigger` actually exists on the target model at save time, preventing runtime crashes from typos.

**ApprovalRuleLine** defines amount ranges (`amount_from` / `amount_to`) and maps each tier to an approver group or specific user. It supports a `require_all` flag for multi-approver scenarios.

SQL constraint ensures only one rule per model per company:
```python
_sql_constraints = [
    ('unique_rule_per_model_company',
     'UNIQUE(model_name, company_id)',
     'An approval rule already exists for this model and company.'),
]
```

Registered the new module in `__init__.py`:
```python
from . import approval_rule
```

- [x] SQL constraint prevents duplicate rules per model/company
- [x] Amount range validation rejects `amount_from >= amount_to`
- [x] Dynamic model selection populates correctly from `ir.model`

**Priority:** High
**Category:** Security / Database

### Task 3: Approval Engine Core Models (Prior Work - Reviewed Today)

**Status:** COMPLETED
**Priority:** High
**Category:** Backend / Architecture

#### Description
Reviewed and validated the existing approval engine architecture consisting of `ApprovalRequest`, `ApprovalLevel`, `ApprovalTransition`, and `ApprovalMixin`. These form the foundation that today's rule system builds on.

#### Files Reviewed
- `custom_addons/spsl_core/models/approval/approvalRequest.py`
- `custom_addons/spsl_core/models/approval/approvalLevel.py`
- `custom_addons/spsl_core/models/approval/approvalMixin.py`

#### Implementation Details
The approval engine follows Odoo's mixin pattern:
- **ApprovalMixin** (`spsl.approval.mixin`): Abstract model that any business model can inherit to gain approval workflow fields (`approval_state`, `approved_by`, etc.) and actions (`action_submit_for_approval`, `action_approve`, `action_reject`, `action_cancel`).
- **ApprovalRequest**: Concrete record tracking each approval with full audit trail (who requested, who approved/rejected, timestamps, rejection reason). Uses `ir.sequence` for reference generation.
- **ApprovalLevel**: Defines approver groups and escalation rules with Many2many relations to `res.users` and `ir.model`.
- **ApprovalTransition**: State machine transitions between levels triggered by approval, rejection, or manual action.

## Technical Implementation Details

### Architecture Decisions
- **Mixin-based design**: The approval system uses Odoo's `_inherit` / AbstractModel pattern, allowing any model to opt into approval workflows by simply inheriting `spsl.approval.mixin`. This avoids code duplication and keeps business logic decoupled.
- **Rule engine pattern**: The new `spsl.approval.rule` / `spsl.approval.rule.line` models implement a threshold-based rule engine. This separates "what needs approval" from "who approves it," making the system configurable by administrators without code changes.

### Challenges Overcome
1. **Dynamic model selection in Odoo 19**: Used `_selection_model_name` querying `ir.model` instead of hardcoding model choices. This makes the rule system future-proof -- any new SPSL model automatically appears in the selection dropdown.
2. **Field existence validation**: Added `_check_field_trigger_exists` constraint that introspects `_fields` at save time. This prevents a common Odoo pitfall where a typo in a Char field (storing a field name) only crashes at runtime during approval processing.
3. **Security CSV correctness**: The original CSV had rows with missing columns and malformed references. Odoo silently ignores bad rows during module installation, which means access rules simply don't apply -- a security hole. Rewrote the entire file with proper 8-column format and verified all foreign key references.

### Query Optimization
- Added database indexes on `model`, `res_id`, `state`, `requested_by`, `approved_by`, and `requested_date` in `ApprovalRequest` for fast lookups.
- `res_model_id` is stored computed (`store=True`) to avoid repeated `ir.model` lookups.
